# 预览渲染坑位记录（Lead 实测，2026-10-02）

## 结论：不要用 `render --input xxx.pptx` 做视觉检查

`libreoffice-kit` 的 **Office 光栅化通道**（backend=libreoffice）会把内容按 **1.5× 放大**，
并从左上角 (0,0) 锚定，于是 PNG 只显示幻灯片左上约 **8.89in × 5.0in**，
右侧 1/3 与下方 1/3 被裁掉。肉眼会误判成"版式全乱"。

**这不是我们文件的问题**——仓库里的旧 PPT 同样如此：

| 证据 | 数值 |
|---|---|
| 标尺实验：1in 方块渲染尺寸 | 179px（应 120px @120dpi）→ 1.49in，即 **1.5×** |
| 标尺实验：x=2in 方块实测起点 | 2.999in（=2×1.5） |
| 标尺实验：x=4in / y=2in 方块实测 | 6.005in / 3.006in（=4×1.5 / 2×1.5） |
| 旧 PPT 顶部蓝带（规格 h=1.875in） | 实测底边 **337px** = 1.875×1.5×120 |
| 降低请求 DPI 到 80 | PNG 尺寸正确（1067px），但内容仍是 1.5× → 与 DPI 无关 |
| PPTX 内部 XML 坐标 | 与规格完全一致（用 python-pptx 回读逐形状核对） |

PDF 导出通道本身是**正确**的（MediaBox = 960.0094×540 pt = 13.333×7.5in）。

## 可信通道：PPTX → PDF → pdfium 光栅化

```
<node> <cli> convert --input deck.pptx --output deck.pdf
<node> <cli> render  --input deck.pdf  --output-dir preview --dpi 120 [--pages 1,2,3]
```

标尺实验复核结果（`_work/ruler/prev_pdf/`，pdfium，120dpi，PNG 1600×900，1in = 120px）：

| 标记 | 规格 | 实测 | 判定 |
|---|---|---|---|
| 红 1in@(0,0) | x=0,y=0,w=1,h=1 | (0, 0.533)-(0.992, 0.992) | ✅ |
| 青 1in@(2,0) | x=2,y=0 | (2.0, …)-(2.992, …) | ✅ 起点精确 |
| 绿 1in@(0,2) | x=0,y=2 | (…, 2.0)-(…, 2.992) | ✅ 起点精确 |
| 橙 2×1in@(4,2) | x=4,y=2,w=2 | (4.0, 2.0)-(5.992, 2.992) | ✅ 宽高精确 |

（红块 y 从 0.533 起是渲染时该图层被后面的通栏蓝带覆盖所致，与坐标无关。）
